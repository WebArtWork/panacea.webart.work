# PANACEA — Roadmap

Snapshot of where the Angular + Firebase migration stands, and what's left before this is
production-ready. Written after porting the static HTML site to Angular 22 and wiring up Firebase
(login + orders), mirroring the pattern used in `~/work/demchukdenys.com`.

## Done

### Angular migration
- Pure-HTML storefront and demo admin fully rebuilt as an Angular 22 app (SSR + prerender), using
  the `@wawjs/ngx-default` template conventions. The Angular project (`codebase/`) is now the repo
  root.
- All pages ported 1:1: catalog/home, product detail, cart, checkout, order confirmation,
  about/production/composition/certificates/delivery/partner/contacts/account,
  privacy/offer/cookies, and the admin shell (dashboard, products, orders, customers, sign-in).
- SEO audited page-by-page: unique title/description/canonical/robots per route, per-product
  OG title/description/image/`og:type` set dynamically, full sitemap + robots.txt regenerated by
  `tools/seo/generate-static-seo.mjs` (previously only listed `/`).
- Assets, company data, and metadata fully rebranded to PANACEA (verified no leftover template
  branding).

### Firebase (this session)
- Firebase project `panacea-d74d5` wired in: `src/app/feature/firebase/firebase.service.ts`
  (lazy, browser-only init of Auth + Firestore) and `auth.service.ts` (sign in/out, auth-state
  signal), mirroring `demchukdenys.com`'s implementation exactly.
- **Login**: `/admin/sign` now does a real `signInWithEmailAndPassword` call. The admin layout
  (`src/app/layouts/admin/admin.component.ts`) gates all four admin pages behind
  `AuthService.ready()` and redirects to `/admin/sign` if there's no session; a "Вийти" button
  signs out.
- **Orders**: `src/app/feature/order/order.service.ts` now reads/writes the `orders` Firestore
  collection instead of `localStorage` (create with a generated `ORD-###-###` id, get by id, list
  all, update status). Checkout writes a real order and redirects to `/order/:id`; the admin
  orders page and dashboard read real orders and can update status live.
- Cloud Firestore is enabled on the Firebase project, with rules already in the console matching
  the reference project: anyone can `create`/`get` a doc in `orders` (needed for anonymous
  checkout and the order-confirmation page), only signed-in users can `list` or `update`/`delete`.
- `admin`, `admin/*`, `admin/sign`, and `order/:id` are now `RenderMode.Client` in
  `app.routes.server.ts` (Firebase Auth/Firestore don't exist during SSR/prerender — these must
  render live in the browser). Verified locally that the existing GitHub Pages `404.html` →
  `index.html` SPA fallback correctly serves and client-renders these routes.
- Build verified clean: no compile errors, initial bundle 380.5 kB (well under the 500 kB budget
  — Firebase loads as a lazy chunk only for checkout/order/admin).

### Explicitly out of scope this round
Products and customers in the admin panel are still local/demo data (`src/data/product`,
`src/data/customer`, browser-storage overrides) — only **login** and **orders** were moved to
Firebase, per the ask. Nova Poshta city/warehouse autocomplete from the reference project was not
ported (PANACEA's checkout form uses a single free-text address field).

## Left to do

1. **Verify the two existing Firebase Auth users are the intended admins** (`esmodeo@gmail.com`,
   `crackeraki@gmail.com` per the console screenshot) — remove any that shouldn't have admin
   access, since anyone with those credentials can sign in and manage orders.
2. **End-to-end test the real login flow** with an actual account — I verified the sign-in page
   renders correctly via the SPA fallback, but didn't have credentials to test a real
   sign-in → dashboard → sign-out round trip.
3. **End-to-end test checkout → Firestore write → order confirmation** with a live browser session
   (add to cart → checkout → confirm the order doc appears in the Firestore console with the right
   shape → confirm `/order/:id` renders it → confirm it shows up in `/admin/orders`).
4. **Firestore rules hardening.** `allow create: if true` on `orders` is fully open — anyone can
   write arbitrary documents to that collection (spam, garbage data, or a large enough flood to
   run up billing). Worth adding field/type validation to the rule (required fields, item count
   caps, reasonable string lengths) and/or Firebase App Check.
5. **Commit a `firestore.rules` file** to the repo (currently only exists in the Firebase console)
   so the rules are version-controlled — same gap exists in the reference project, worth fixing
   here since orders are real user data now.
6. **Decide on password reset / user management.** There's no "forgot password" flow and no way to
   add a new admin except through the Firebase console by hand.
7. **Consider moving products and customers to Firestore too**, once there's a real need to manage
   the catalog from more than one browser/device — the current local-storage approach means
   product edits only exist on the device that made them.
8. **Redeploy and smoke-test on the real domain** (`panacea.webart.work`) — this was only verified
   against a local static server standing in for GitHub Pages; the actual GH Pages headers/rewrite
   behavior should be confirmed to match.
